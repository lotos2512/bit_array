# BitArray

Массив битов переменной длины с **разрежённым хранением**: занимает память только за установленные биты, а не за всю ёмкость.

---

## Зачем использовать

**BitArray** подходит, когда нужно:

- **Проверять принадлежность к множеству по индексу** — «есть ли элемент с номером N» (например, ID пользователя, хеш, индекс в справочнике). Один бит = один элемент множества.
- **Хранить большой объём флагов при малой заполненности** — например, 8 млн слотов, а занято 10 тысяч. Обычный `[]bool` или `[]int64` занял бы мегабайты; BitArray хранит только непустые «слова».
- **Быстро проверять пересечение двух множеств** — метод `Intersection(other)` за O(размер данных), без перебора всех битов.
- **Мигрировать со старых данных** — из плотного `[]int64` можно построить BitArray через `NewBitArrayFromData(data)` и дальше работать по новой схеме без лишней копии всего массива.

### Примеры задач

| Задача | Как помогает BitArray |
|--------|------------------------|
| «Есть ли номер X в списке разрешённых» | Один бит на номер; проверка за O(1) в dense, O(log k) в sparse при k непустых bucket'ах. |
| Кэш «уже обработали индекс i» | Ёмкость = максимум индекса, хранятся только установленные биты. |
| Фильтр по ID (миллионы возможных, тысячи реальных) | Массив на 8M бит занимает порядка сотен KB вместо мегабайта. |
| Проверка «все ли элементы A есть в B» | `A.Intersection(B)` без построения новых структур. |

## Как устроен алгоритм

Внутри используются **три режима** в зависимости от того, сколько битов установлено.

### 1. Режим `sparseIndices` (очень мало битов, ≤64)

- **Хранится:** отсортированный slice индексов установленных битов `[]uint64`.
- **Память:** 8 байт на один установленный бит.
- **SetBit:** вставка в отсортированный slice (логарифмический поиск + сдвиг).
- **GetBit:** бинарный поиск по индексу.

Используется сразу после создания, пока установлено не больше 64 битов.

### 2. Режим `sparseList` (средне: много битов, но мало непустых «слов»)

- **Хранится:** отсортированный slice пар `(номер bucket'а, слово из 64 бит)` — только те слова, где хотя бы один бит установлен.
- **Память:** 16 байт на одно непустое 64-битное слово (bucket).
- **SetBit/GetBit:** номер бита переводится в `(bucket, позиция в слове)`; по bucket'у делается бинарный поиск в slice, затем чтение/запись бита в слове.

Переход из `sparseIndices`: когда установленных битов становится больше 64, индексы конвертируются в пары (bucket, word) и дальше используется только `sparseList`.

### 3. Режим `data` (dense — много непустых bucket'ов)

- **Хранится:** полный slice `[]int64` длины «ёмкость/64» — классический массив битов.
- **Память:** 8 байт × количество слов (например, 1 MB для 8M бит).
- **SetBit/GetBit:** прямой доступ по индексу слова и позиции в слове — O(1).

Переход в dense: когда число непустых bucket'ов в `sparseList` превышает **половину** от общего числа слов (`size/2`). Тогда выделяется полный slice и данные копируются в него — дальше работа идёт только с ним.

### Схема переключений

```
NewBitArray(N)
       │
       ▼
  sparseIndices (до 64 установленных битов)
       │
       │  больше 64 битов
       ▼
  sparseList (только непустые bucket'ы)
       │
       │  непустых bucket'ов > 50%
       ▼
  data (dense: полный []int64)
```

### Формула «бит → bucket и позиция»

- **bucket** = индекс бита / 64  
- **позиция в слове** = индекс бита % 64  

Один `int64` хранит 64 подряд идущих бита; слово может быть 0 (все нули) или любая маска битов.

## API (кратко)

| Действие | Метод |
|----------|--------|
| Создать по ёмкости в битах | `NewBitArray(capBits)` |
| Создать из старых данных `[]int64` | `NewBitArrayFromData(data)` |
| Установить/снять/инвертировать бит | `SetBit(i)`, `SetBitMust(i)`, `unSetBit(i)`, `inverseBit(i)` |
| Массовая установка по списку индексов | `SetBits(indices []uint64)` — быстрее цикла SetBitMust, при пустом массиве строит sparseList за один проход |
| Проверить бит | `GetBit(i) bool` |
| Число установленных битов | `Count() uint64` |
| Ёмкость в битах | `Capacity() uint64` |
| Только непустые bucket'ы (без аллокации полного slice) | `SparseBuckets() map[uint64]int64` |
| Полный массив слов (аллоцирует slice длины cap/64) | `GetData() []int64` |
| «Все биты из other есть в t» | `t.Intersection(other) bool` |
| Загрузить плотные данные «как есть» | `SetData(data []int64)` |
| **Сохранить в БД / загрузить** | `WriteTo(w io.Writer)`, `ReadFrom(r io.Reader)` |

**Рекомендация:** при разрежённых данных предпочитайте `SparseBuckets()` вместо `GetData()`, чтобы не выделять мегабайт под полный slice.

### Сохранение и загрузка (как у Roaring)

BitArray можно сериализовать в поток байт и сохранить в БД, затем быстро загрузить без пересчёта:

```go
var buf bytes.Buffer
_, _ = ba.WriteTo(&buf)
db.SaveBlob(buf.Bytes())

// Загрузка
loaded := &bit_array.BitArray{}
_, _ = loaded.ReadFrom(bytes.NewReader(dbBlob))
```

Формат бинарный (магия + size, cap, тип хранения + данные). Подходит для BLOB в БД или файла.

### Параллельный доступ (thread-safe при чтении)

**Безопасно для параллельного чтения:** несколько горутин могут одновременно вызывать `GetBit`, `Capacity`, `GetSize`, `GetData`, `SparseBuckets`, `Intersection` и другие методы, не изменяющие массив, — гонки данных не возникает.

Если одна горутина пишет (`SetBit`, `unSetBit`, `inverseBit`, `SetData`), а другая читает, синхронизацию (например, `sync.RWMutex`) должен обеспечить вызывающий код.

## Пример

```go
// Множество на 8 миллионов «слотов»; реально ставим несколько битов
ba := bit_array.NewBitArray(8_000_000)
ba.SetBitMust(1)
ba.SetBitMust(7999)
ba.SetBitMust(7_000_000)

fmt.Println(ba.GetBit(1))       // true
fmt.Println(ba.GetBit(2))       // false
fmt.Println(ba.Capacity())      // 8000000

// Только непустые слова — без выделения 1 MB
buckets := ba.SparseBuckets()   // map[0:2, 124:..., 109375:1]
fmt.Println(len(buckets))       // 3

// Загрузка из старых данных
old := []int64{0x6, 0, 0, 0}
ba2 := bit_array.NewBitArrayFromData(old)
fmt.Println(ba2.GetBit(1), ba2.GetBit(2))  // true true
```

## Сравнение с другими библиотеками

Запуск: `go test -bench=BenchmarkCompare -benchmem ./...`  
Ёмкость задаётся в коде (`compareCap`, напр. 8M или 80M). Сравнение при **80M бит** — в [BENCHMARKS.md](BENCHMARKS.md).

Участвуют: **bit_array** (наша), **bitset** (github.com/bits-and-blooms/bitset), **Roaring** (github.com/RoaringBitmap/roaring, сжатый битмап для множеств целых).

### Память (ёмкость до 8M бит)

| Сценарий | bit_array | bitset | Roaring |
|----------|-----------|--------|---------|
| Только создание (New) | **0 B** | **~1 MB** | **0 B** |
| 3 установленных бита | **~48 B** | ~1 MB | ~64 B |
| 16k бит (каждый 500-й, SetBits) | **~65 KB** | **~1 MB** | ~132 KB |
| Intersection (sparse) | **0 B** | **~1 MB** | **~144 B** |
| Плотное заполнение | ~1 MB | ~1 MB | зависит от данных |

При разрежённых данных **bit_array** и **Roaring** экономят память; bitset всегда держит полный массив.

### На сколько Roaring лучше по памяти (разные сценарии)

Ёмкость 8M бит, разное число установленных битов. Запуск: `go test -bench=BenchmarkCompare_Memory -benchmem ./...`

| Установлено битов | bit_array | Roaring | Roaring меньше в |
|-------------------|-----------|---------|------------------|
| 3                 | 248 B     | 128 B   | **≈2×** |
| 100               | ~9 KB     | ~8 KB   | ≈1.1× (паритет) |
| 1 000             | ~73 KB    | **~12 KB** | **≈6×** |
| 16 000 (каждый 500-й, **SetBits**) | **~65 KB** | ~129 KB | **bit_array ≈2× компактнее** |

При массовой установке через **SetBits** в режиме «один бит на bucket» bit_array хранит индексы в **sparseIndices32** (4 байта на бит) и по памяти выигрывает у Roaring (~65 KB vs ~132 KB).

### GetBit: результаты

Замеры: `go test -bench='BenchmarkCompare_GetBit' -benchmem ./...`

| Режим | bit_array | bitset | Roaring | Кто быстрее |
|-------|-----------|--------|---------|--------------|
| **Sparse (3 бита, 8M ёмкость)** | ~3.2 ns | **~0.44 ns** | ~4.7 ns | **bitset** (~7× быстрее нас) |
| **Dense (каждый 2-й бит, 64k)** | ~1.7 ns | **~0.74 ns** | — | **bitset** (~2× быстрее) |

У bitset GetBit — прямой доступ по индексу в slice (уже выделен 1 MB), поэтому он быстрее всех. У bit_array в sparse — бинарный поиск по sparseList (~3 ns); в dense — доступ по индексу (~1.7 ns). У Roaring — поиск по сжатой структуре (~4.7 ns). Все варианты без аллокаций в горячем цикле (0 B/op, 0 allocs/op).

### Скорость (сводная)

| Операция | bit_array | bitset | Roaring |
|----------|-----------|--------|---------|
| New | **~0.19 ns, 0 allocs** | ~76 µs, 1 MB | **~0.19 ns, 0 allocs** |
| SetBit (3 бита) | **~8 ns, 0 allocs** | **~3.7 ns** | ~75 ns, 4 allocs |
| GetBit (sparse) | ~3.2 ns | **~0.44 ns** | ~4.7 ns |
| GetBit (dense) | ~1.7 ns | **~0.74 ns** | — |
| FillEvery500 (16k бит, цикл SetBit) | ~346 µs | **~123 µs** | **~106 µs**, 132 KB |
| **FillEvery500 через SetBits (bulk)** | **~57 µs**, **~65 KB** | — | ~106 µs, 132 KB |
| Intersection (sparse) | **~9 ns, 0 allocs** | ~127 µs, 1 MB | ~84 ns, 144 B |

**Итог:** по **массовой установке** (16k бит) **bit_array** с **SetBits** быстрее Roaring (~57 µs vs ~106 µs) и **компактнее по памяти** (~65 KB vs ~132 KB). По **GetBit** быстрее всего **bitset** (прямой доступ к массиву). bit_array — посередине (в dense ~1.7 ns, в sparse ~3.2 ns). Roaring в sparse ~4.7 ns. По остальным операциям: bit_array сильнее на New и Intersection; Roaring — при **16k бит циклом SetBit** всё ещё компактнее (~1.75×); при 3/100/1000 бит мы наравне или лучше (см. [BENCHMARKS.md](BENCHMARKS.md)).
